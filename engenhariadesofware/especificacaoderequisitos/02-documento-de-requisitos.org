* Introdução
** Necessidade do sistema
A evasão escolar raramente é um evento súbito: costuma ser precedida por
sinais (faltas, queda de desempenho, problemas sociais). Esses sinais ficam
dispersos entre professores, secretaria e orientação, o que atrasa a
intervenção. O sistema deve reunir esses sinais, apontar alunos em risco e
apoiar o acompanhamento das ações tomadas.
** Escopo
- *Dentro do escopo:* registro/importação de dados escolares, indicador de
  risco, alertas, registro de intervenções, relatórios, exportação para pesquisa.
- *Fora do escopo (a confirmar):* substituir o sistema acadêmico oficial,
  emissão de documentos oficiais.
** Relação com objetivos da organização
(preencher após o estudo de viabilidade)

* Glossário
- Evasão :: abandono da escola pelo aluno sem conclusão do curso/série
  (definição operacional a ser fixada com stakeholders).
- Abandono :: (diferenciar de evasão conforme definição do INEP).
- Aluno em risco :: aluno cujo indicador de risco ultrapassa o limiar configurado.
- Intervenção :: ação registrada para evitar a evasão (contato, reunião, encaminhamento).
- Stakeholder :: pessoa ou grupo afetado pelo sistema ou que influencia seus requisitos.

** Requisitos funcionais
*** RF-01 Registrar frequência por turma                         :HIPOTESE:
:PROPERTIES:
:ID:         RF-01
:TIPO:       funcional
:PRIORIDADE: deve
:STATUS:     proposto
:ORIGEM:     RU-01
:END:
- *Descrição:* O sistema deve permitir que o professor registre a presença
  dos alunos de uma turma em uma data.
- *Justificativa:* frequência é o principal sinal precoce de evasão.
- *Critério de aceitação:* o registro de uma turma de 40 alunos pode ser
  concluído em até 2 minutos.

*** RF-02 Importar dados do sistema acadêmico                    :HIPOTESE:
:PROPERTIES:
:ID:         RF-02

** Requisitos não funcionais
Classificação de Sommerville (fig. 4.3): requisitos de *produto*
(usabilidade, eficiência, confiança, proteção), *organizacionais*
(ambientais, operacionais, de desenvolvimento) e *externos*
(regulatórios, éticos, legais). Devem ser quantificados sempre que possível
(fig. 4.5: velocidade, tamanho, facilidade de uso, confiabilidade,
robustez, portabilidade).

*** RNF-08 Uso do App Shell fzl-fund-appshell--lit (organizacional/desenvolvimento)
:PROPERTIES:
:ID:         RNF-08
:TIPO:       nao-funcional/organizacional
:PRIORIDADE: deve
:STATUS:     aprovado
:FONTE:      Decisão da equipe (Wagner Marques), 2026-10-06
:REFERENCIA: https://github.com/wagnermarques/fzl-fund-appshell--lit
:END:
- *Descrição:* A interface do sistema deve ser construída sobre o App Shell
  [[https://github.com/wagnermarques/fzl-fund-appshell--lit][fzl-fund-appshell--lit]], herdando sua stack e seu padrão de camadas:
  - componentes de UI como Web Components em Lit, com Material Web (Material 3);
  - build com Vite e distribuição como PWA instalável (vite-plugin-pwa/Workbox);
  - roteamento por /hash router/ (compatível com hospedagem estática);
  - estado local /offline-first/ via /storage-service/;
  - backend: o [[https://github.com/wagnermarques/fzlbpms][fzlbpms]] (bundles Apache Camel rodando no Apache Karaf,
    um por front-end de projeto);
  - configuração declarativa via =appshell.config.js= (=defineAppShellConfig=).
  As funcionalidades do sistema devem ser implementadas como componentes e
  rotas carregados dentro desse shell.
- *Justificativa:* reaproveitar uma base técnica já definida e testada pelo
  grupo, padronizar os projetos e herdar PWA, offline e acessibilidade.
- *Critério de aceitação:* todas as telas são rotas/componentes do App Shell,
  sem uma estrutura de aplicação paralela; a versão do App Shell utilizada
  está declarada em =package.json=.

*** RNF-09 Acessibilidade (produto/usabilidade)                  :HIPOTESE:
:PROPERTIES:
:ID:         RNF-09
:TIPO:       nao-funcional/produto
:PRIORIDADE: deveria
:STATUS:     proposto
:ORIGEM:     RNF-08
:END:
O sistema deveria manter os recursos de acessibilidade do App Shell: fontes
Atkinson Hyperlegible e OpenDyslexic, temas claro, escuro e de alto
contraste, e ampliação de texto de 1x a 2x.

*** Pontos a negociar decorrentes do RNF-08
O App Shell foi pensado para apps que funcionam sem conta e sem backend.
Este sistema trata dados pessoais de menores, por isso estes pontos precisam
ser resolvidos junto com RNF-04 e RNF-05:
- *Dados locais:* dados de alunos guardados em =localStorage= ficam em
  dispositivos possivelmente compartilhados na escola. Definir o que pode ser
  armazenado localmente, e se o armazenamento deve ser cifrado ou limpo ao sair.
- *Backend obrigatório:* aqui o backend (fzlbpms, bundle Camel/Karaf deste
  projeto) e a autenticação provavelmente serão obrigatórios, e não opcionais como no App Shell.
- *Hospedagem:* GitHub Pages serve o front-end; definir onde os dados ficam
  hospedados para atender à LGPD.
- *Analytics:* o App Shell tem suporte a GA4. Avaliar se o uso é permitido com
  usuários menores de idade, ou desativá-lo.
